# RCA — Redeploy build_image failure (run 7441f8cf-fdec-4fe0-acdc-d88545975003)

## Deployment
- App: `gta-quest-map` (Expo / EAS, template `expo_mongo_base_image_eas`)
- Failed run: `7441f8cf-fdec-4fe0-acdc-d88545975003` (redeploy, 2026-11-25 20:05)
- Last good run still live: `f9c61e8d-62c3-4241-aa77-7c4faa99e3e3`

## Symptom
`build_image` fails in the **EAS OTA lane** (runs in parallel with docker-build inside Cloud Build). Build log tail:

```
[EAS_LOG] Initializing EAS project...
Using EAS CLI without version control system is not recommended...
Failed to get Git root path with `git rev-parse --show-toplevel`. Error: ... code: 128
Falling back to using current working directory as project root.
You can set `EAS_PROJECT_ROOT` environment variable...
/workspace/frontend/node_modules/expo/bin/cli config --json exited with non-zero code: 1
    Error: project:init command failed.
```

## Root cause
`eas project:init` internally runs `expo config --json`, and **that** is the command exiting 1 — not git. The `git rev-parse ... code 128` line is a benign fallback (the build sets `EAS_NO_VCS=1`; it correctly falls back to the working dir and continues).

`expo config --json` fails because of a **stale SDK-57 dependency left behind by the SDK 57→58 upgrade**. The app was migrated to Expo SDK 58 (`frontend/patch-sdk58-upgrade.py`, plus `package.json.sdk57.bak` / `yarn.lock.sdk57.bak` backups in the repo). The migration bumped `expo` to `^58.0.0` and aligned every other package to `~58.0.x`, **except `@expo/log-box`, which is still pinned at `^57.0.4`** in `frontend/package.json`.

`@expo/log-box` is an internal Expo package loaded by the SDK-58 module graph. The failing build's own yarn install flagged the conflict directly:

```
warning " > @expo/metro-runtime@58.0.16" has incorrect peer dependency "@expo/log-box@^58.0.14".
warning " > expo-router@58.0.29"        has incorrect peer dependency "@expo/log-box@^58.0.14".
warning " > @expo/log-box@57.0.4"       has incorrect peer dependency "@expo/dom-webview@^57.0.1".
```

A cross-major mismatch of this internal package (57 vs the SDK-58 line `^58.0.14`) breaks `expo` CLI config resolution, so `expo config --json` exits 1 and `project:init` aborts.

### Why it was intermittent (16:08 fail → 16:23/16:33 pass → 20:05 fail)
Yarn's resolution of a conflicting peer tree is non-deterministic across fresh installs — sometimes a compatible 58 copy of `@expo/log-box` got hoisted via a transitive dep, sometimes the top-level pin (57.0.4) won. That is why earlier redeploys occasionally passed. The underlying defect (the stale pin) has been present the whole time; the fix removes the ambiguity deterministically.

## Confidence / what was verified
- Verified statically in the eph sandbox: `app.json` is valid JSON; both local config plugins (`plugins/withBuildConfig.js`, `plugins/withRemoveMediaPermissions.js`) parse with no syntax errors; `@expo/log-box` confirmed pinned `^57.0.4` while `expo` is `^58.0.0` and siblings are `~58.0.x`.
- NOT end-to-end reproduced: `expo config --json` could not be executed in the sandbox because a full `yarn install` of this SDK-58 dependency tree OOM-kills the sandbox pod (exit 137) on every attempt. Root cause is therefore established from the real Cloud Build log + static dependency analysis, not from an in-pod rerun.

## Fix (owner: E1, in the source environment — `frontend/`)
1. Align `@expo/log-box` with SDK 58. In `frontend/package.json`, change:
   ```
   "@expo/log-box": "^57.0.4"
   ```
   to the SDK-58 line (satisfies the `^58.0.14` peer requirement of expo-router / metro-runtime):
   ```
   "@expo/log-box": "~58.0.14"
   ```
   Preferred equivalent: run `npx expo install @expo/log-box` (or `npx expo install --fix`) in `frontend/` so Expo picks the exact SDK-58-compatible version and updates `yarn.lock`.
2. Run `yarn install` in `frontend/` to refresh `yarn.lock` with the aligned version.
3. (Recommended) run `npx expo-doctor@latest` to confirm no other SDK-57 remnants survived the upgrade.
4. Re-trigger the deploy. The EAS lane's `eas project:init` / `expo config --json` should then succeed.

## Not the cause (do not chase)
- `git rev-parse` code 128 — expected; `EAS_NO_VCS=1` handles it.
- The deployer EAS script / manifests — unchanged, infra-side, not editable per-app; the fault is in the app's `frontend/package.json` deps.
